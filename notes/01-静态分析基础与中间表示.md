# 静态程序分析基础与中间表示：从可判定边界到可计算模型

> 本文重组自系列第 1～3 篇材料，目标是建立一条可复用的学习主线：**课程要解决什么问题 → 为什么只能近似 → 如何表达程序 → 如何在表达上计算性质**。本文不是原文复述；示例、术语边界与若干技术表述均已校正。

## 0. 学习地图与课程定位

这门课程面向软件安全方向研究生，采用“理论 + 工程实践”的组合：

- **理论侧**：程序分析的计算理论边界，抽象解释、控制流/数据流、过程间分析、指针分析等核心方法；
- **表示侧**：从源代码进入 CST、AST、CFG、3AC、SSA、LLVM IR 等不同层次的中间表示（IR）；
- **实践侧**：使用 YASA 这一开源、多语言静态分析框架，编写 Checker，完成 AST 查询、数据流分析、调用图分析等任务；可通过 SDK、统一声明式查询语言 UQL 或 MCP 使用其能力；
- **研究侧**：理解分析引擎设计，在 YASA/UAST 之上实现或验证新的分析方法，并参与开源协作。

课程的前置关系不是“先记工具 API”，而是：

```text
程序语义与可达状态
  ├─ 计算理论边界：停机问题、Rice 定理
  ├─ 可计算折中：过近似/欠近似、抽象/搜索
  ├─ 结果契约：soundness、completeness、may/must
  └─ 程序表示：源代码 → AST/CST → CFG/3AC → SSA/LLVM IR
                               └→ YASA-UAST（保留较高层源语言结构）
```

静态分析不是单一算法，而是三项设计选择的组合：

1. **要回答什么性质**（如“是否可能空指针解引用”）；
2. **用什么程序表示**（AST、CFG、SSA 等）；
3. **允许何种近似及代价**（误报、漏报、耗时、内存）。

## 1. 为什么需要程序分析

大型软件横跨操作系统、云服务、游戏、车机、智能合约和关键基础设施。复杂性带来的逻辑错误、安全漏洞与性能问题，往往无法仅靠人工审查发现。Cloudflare 服务中断、Log4Shell（CVE-2021-44228）等案例说明：一个边界条件、错误处理缺失或输入验证缺陷，就可能沿依赖链放大为系统性故障。

### 1.1 动态分析与静态分析

设程序为 \(P\)，输入集合为 \(I\)，一次具体执行轨迹记为 \(\tau(P,i)\)。

**动态分析**执行程序，观察有限个具体输入上的轨迹：

\[
T_{obs}=\{\tau(P,i)\mid i\in I_{tested}\},\qquad I_{tested}\subseteq I
\]

典型方法包括：

- 压力/负载测试；
- 基于模型生成测试；
- 模糊测试（fuzzing）；
- 动态污点、运行时监控、性能剖析；
- concolic execution（具体执行与符号约束结合）。

优点是证据贴近真实执行，能获得运行时值、堆栈和环境信息；局限是覆盖受输入、调度、环境及时间预算约束。发现一次崩溃通常能给出可复现证据，但“动态分析没有误报”不是普遍定理：测试 oracle 错误、插桩改变时序、环境不一致或规则误分类仍可能产生错误告警。

**静态分析**不通过运行待分析程序来获得结论，而对代码或其中间表示做推理。典型方法包括：

- AST 模式查询；
- 控制流、数据流、调用图和指针分析；
- 抽象解释；
- 模型检测；
- 符号执行（通常归为静态或混合方法，视是否实际运行目标程序而定）。

静态分析可在编译前、提交时或 IDE 内运行，容易自动化并能覆盖测试尚未执行的代码。不过“静态分析会分析所有路径”也不是定义：有的静态分析做全局过近似，有的符号执行只探索预算内路径，有的工具主动牺牲 soundness 换取速度。

二者关系不是替代，而是互补：静态分析给出广覆盖候选，动态方法复现或验证候选；动态轨迹也可反过来改进静态模型。

## 2. 理论边界：停机问题与 Rice 定理

### 2.1 停机问题

假设存在总能在有限时间返回且完全正确的判定器：

\[
H(P,i)=
\begin{cases}
\texttt{true}, & P(i)\text{ 停机}\\
\texttt{false}, & P(i)\text{ 不停机}
\end{cases}
\]

构造程序 \(D\)：

```python
def D(x):
    if H(x, x):
        while True:
            pass
    else:
        return 0
```

令输入为程序自身编码 \(D\)：

- 若 \(H(D,D)=\texttt{true}\)，按 `D` 的定义它无限循环；
- 若 \(H(D,D)=\texttt{false}\)，按 `D` 的定义它立即返回。

两种答案都与判定器声称的行为矛盾。因此，不存在对任意程序与输入都终止且完全正确的停机判定器。

这里的关键限定是**任意程序、任意输入、有限时间、答案完全正确**。对有限状态程序、带循环界的程序或其他受限语言，停机及许多性质可以判定。

### 2.2 Rice 定理究竟说什么

对图灵完备模型中程序计算的**部分函数**，任何非平凡的、只依赖程序所计算语义而非源代码写法的性质，都是不可判定的；对可识别语言也有相应的 Rice 定理版本。

- **语义/外延性质**：只要两个程序计算同一部分函数，就应具有相同答案；
- **非平凡**：至少一个可计算函数具有该性质，至少一个不具有；
- **不可判定**：不存在对所有输入都终止且正确回答是/否的算法。

例如“程序计算的函数是否恒为 0”是语义性质；“源文件是否含字符串 `malloc`”是语法性质，不受 Rice 定理直接约束。诸如“内存泄漏”“数组越界”依赖具体的机器、资源、异常与执行语义，不能只用一句 Rice 定理草率覆盖；通常要在明确语义后，通过停机问题归约证明相应全程序判定问题不可判定。

一个更规范的缺陷归约模板是：给定任意 \((P,i)\)，构造程序 \(R_{P,i}\)：

```c
void R(void) {
    run_P_on_i();      // 若 P(i) 不停机，控制流永远不到下一行
    trigger_bug();     // 若 P(i) 停机，确定触发待判定缺陷
}
```

若存在能判定“`R` 的某次执行是否可到达 `trigger_bug`”的通用算法，就能借它判定 \(P(i)\) 是否停机，矛盾。实际归约必须定义 `run_P_on_i`、输入量词和“缺陷”的操作语义，不能让被构造程序在运行时直接调用假想分析器并忽略自指编码问题。

### 2.3 不可判定不等于不可分析

不可判定否定的是“对所有程序都终止、零误差的通用判定器”，并不妨碍：

- 对受限语言得到精确结果；
- 对部分实例精确、对其他实例返回 unknown；
- 用近似换取总能终止；
- 用超时、路径预算换取可用结果；
- 结合人工不变量或证明提示完成验证。

工程问题由此转化为：**怎样让误差方向可解释，并让代价可接受？**

## 3. 近似：真实语义、过近似与欠近似

设程序所有真实可达状态（或轨迹）为 \(R\)，分析计算的集合为 \(A\)。

### 3.1 两个方向

**过近似（over-approximation）**满足：

\[
R\subseteq A
\]

它不遗漏真实行为，但 \(A\setminus R\) 中可能包含伪行为。若在 \(A\) 中都找不到坏状态，则真实执行中也没有坏状态；若在 \(A\) 中发现坏状态，可能是假阳性，需进一步验证。

**欠近似（under-approximation）**满足：

\[
A\subseteq R
\]

每个纳入结果的行为都有真实见证，但可能只覆盖 \(R\) 的一部分。找到坏轨迹即可证明缺陷存在；没找到不能证明安全。

用集合表达告警语义最清楚。设坏状态集合为 \(B\)：

- 过近似：若 \(A\cap B=\varnothing\)，则 \(R\cap B=\varnothing\)；
- 欠近似：若找到 \(s\in A\cap B\)，则 \(s\in R\cap B\)。

### 3.2 随机数示例（修正版）

```python
import random
r = random.random()       # 0.0 <= r < 1.0
out = "yes"
if r < 0.5:
    out = "maybe"
if r == 1.0:              # 不可行分支
    out = "no"
print(out)
```

真实输出为 `"yes"` 或 `"maybe"`，不是 `"yes"` 或 `"no"`。若分析器只知道 `r` 是任意浮点数，可能算得：

\[
A=\{\text{"yes"},\text{"maybe"},\text{"no"}\}
\]

这相对真实集合 \(R=\{\text{"yes"},\text{"maybe"}\}\) 是过近似。若测试恰好见证了 `r=0.25`，只得到 \(A=\{\text{"maybe"}\}\)，则是欠近似。

欠近似**不是**“仅保留所有执行都会经过的路径”，也不是“假定所有分支条件都不成立”。那描述的是某条任意选择的路径，未必有可执行见证；“所有执行都满足”的必然性质则是另一个量词问题。

## 4. 获得近似的两条主线：抽象与搜索

### 4.1 抽象法

设具体状态集合为 \(C\)，具体 collecting transformer、抽象化、具体化和抽象转移的类型分别为：

\[
F:\mathcal P(C)\to\mathcal P(C),\qquad
\alpha:\mathcal P(C)\to A^\#,
\]

\[
\gamma:A^\#\to\mathcal P(C),\qquad
F^\#:A^\#\to A^\#.
\]

若 \(\alpha\dashv\gamma\) 构成 Galois 连接，则 sound 的抽象转移应满足：

\[
F(\gamma(a))\subseteq\gamma(F^\#(a)).
\]

在 \(F\) 与 \(F^\#\) 单调、函数之间采用点态序的条件下，等价地可写为：

\[
\alpha\circ F\ \sqsubseteq\ F^\#\circ\alpha.
\]

数据流分析通常在 CFG 上反复应用转移函数并求不动点；遇到无限升链时使用 widening，必要时再 narrowing。区间域、符号域、常量域、空值域、指针/别名域都是常见抽象域。

抽象法常用于控制流/数据流、过程间、调用图、指针分析。SVF、Infer、WALA、Tai-e、YASA 等框架各自包含多种算法，不能仅凭工具名称断言它们所有能力都来自同一种抽象解释实例。

### 4.2 搜索法

搜索法枚举输入、路径或状态：测试、fuzzing、符号执行、concolic execution 都可从这一视角理解。它通过约束求解、启发式、状态合并、剪枝和预算控制路径爆炸。

纯符号执行把输入记为符号，并累积路径条件。例如：

```c
if (x > 0) y = x + 1;
else       y = -x;
```

两条路径分别携带 \(x>0\) 与 \(x\le 0\)。求解器给出满足路径条件的具体输入，就得到可执行见证。但循环、递归、复杂堆结构及求解器理论限制使完备探索通常不可行。

抽象和搜索不是互斥分类：符号执行可以合并状态形成过近似，抽象解释也可拆分路径；现代工具经常混用二者。

## 5. 示例抽象域：符号分析

目标：不计算整数表达式的精确值，只判断结果为正、负或零。

可用的抽象元素是具体整数集合的分类：

\[
Sign=\{\bot,\mathsf{Neg},\mathsf{Zero},\mathsf{Pos},\top\}
\]

其含义为：

\[
\gamma(\mathsf{Neg})=\{n\in\mathbb Z\mid n<0\},\quad
\gamma(\mathsf{Zero})=\{0\},\quad
\gamma(\mathsf{Pos})=\{n\in\mathbb Z\mid n>0\}
\]

\(\bot\) 表示无具体值/不可达，\(\top\) 表示符号未知。偏序按具体化集合包含关系定义：\(\bot\) 在底部，三种确定符号互不比较，\(\top\) 在顶部。

抽象运算必须覆盖所有具体组合。例如：

| \(\oplus\) | Neg | Zero | Pos |
|---|---:|---:|---:|
| Neg | Neg | Neg | \(\top\) |
| Zero | Neg | Zero | Pos |
| Pos | \(\top\) | Pos | Pos |

乘法有 \(Neg\otimes Neg=Pos\)、\(Neg\otimes Pos=Neg\)、\(Zero\otimes x=Zero\)。除法必须单独建模“除零异常”：最好把正常整数结果与异常状态分开，例如产品域 `Sign × MayDivZero`；把 `undefined` 直接塞进符号格却又规定“零乘任意为零”，容易混淆求值语义——若操作数表达式本身先抛异常，乘法不会产生零。

“unknown”也不等于语言值 `undefined`：前者是分析器知识不足，后者若存在则是具体语言语义中的值或异常。准确区分 \(\bot\)、\(\top\)、异常和值域，是后续理解数据流分析的前提。

## 6. Soundness、Completeness 与 may/must

### 6.1 先固定查询与正例

这组术语极易因领域惯例相反而混乱。设真实正例集合为 \(T\)，分析报告正例集合为 \(A\)：

- **sound（报告可靠）**：\(A\subseteq T\)，无假阳性（FP）；
- **complete（不漏正例）**：\(T\subseteq A\)，无假阴性（FN）。

这是逻辑推理/分类视角。安全分析文献还常把“sound bug analysis”用来表示“不会漏掉任何可能错误”，即上式的 complete；因为它把“安全证明”而不是“缺陷告警”视为分析结论。阅读论文时必须问：**正例是什么？工具是在证明安全，还是报告缺陷？** 不能脱离查询方向说“过近似必然 sound”。

若采用验证视角，过近似的安全证明是 sound：分析器说“抽象状态里无错”时，真实程序确实无错；但过近似给出的某条告警未必是真缺陷。欠近似找到具体坏轨迹时，该缺陷结论是 sound；但没找到不代表安全。

同时满足 sound 与 complete 并非任何场景都不可能：有限状态/受限语言上可以；对某些性质，允许分析器不终止也可能半判定。不可判定性排除的是对一般图灵完备程序、对目标非平凡语义性质、总终止且两边都精确的判定器。

### 6.2 May 与 must 是路径量词，不是近似方向的同义词

- **may 性质**：\(\exists\) 一条执行满足 \(Q\)，如“变量可能未初始化”“可能到达错误点”；
- **must 性质**：\(\forall\) 相关执行都满足 \(Q\)，如“到达使用点时变量必已初始化”。

数据流框架中，may 分析常以并集汇合可能事实，must 分析常以交集汇合必然事实，但具体 lattice 方向取决于事实如何编码。

过近似可用于 sound 地证明 may 性质的否定：抽象上都不可达，则真实上不可达；抽象上“可能”只表示候选，不保证真实存在。类似地，must 分析若受近似影响，报告“不必然”也未必就提供真实反例。may/must、over/under、sound/complete 是三组有关联但不能机械一一对应的概念。

### 6.3 为什么许多安全工具重视保守性

编译优化若错误断言“该值永远非空”并据此删除检查，会改变程序语义；验证工具若漏掉真实攻击路径，会给出虚假的安全感。因此这些场景往往选择能支持保守安全证明的过近似。代价是误报，工程上再通过上下文敏感、流敏感、路径敏感、别名精化或动态验证降低误报。

类型转换例可表达为：字段 `a.fld` 可能指向 `B` 或其兄弟类型 `C`。若分析忽略 `C` 的赋值，可能错误地接受 `(B) a.fld`；保守指向集包含 `{B,C}`，则拒绝证明转换安全。这里结论是“无法证明安全/可能不安全”，不等价于声称某次运行一定失败。

## 7. 从源代码到中间表示：编译流水线

一个典型编译器前端到后端的流程是：

```text
字符流
  → 词法分析：Token 流
  → 语法分析：CST/Parse Tree，常进一步得到 AST
  → 语义分析：名称绑定、作用域、类型检查等带注解表示
  → IR 生成/降低（lowering）
  → 机器无关优化
  → 指令选择、寄存器分配、调度等后端阶段
  → 目标代码
```

符号表、类型环境和诊断系统通常横跨多个阶段，而非孤立的一次输入输出。

### 7.1 词法、语法、语义

- **词法分析**按词法规则切出标识符、关键字、字面量和标点。注释/空白是否丢弃取决于用途；格式化器和源码变换工具常需保留 trivia。
- **语法分析**按上下文无关文法组合 Token，识别优先级、结合性与嵌套结构。注意 CFG 在这里是 *Context-Free Grammar*，后文 CFG 是 *Control-Flow Graph*。
- **语义分析**完成名称解析、作用域和类型规则等静态语义检查。“语法正确”不代表类型正确，但也不能说语义分析能捕获一般“逻辑错误”。常量折叠通常归优化阶段，虽然具体编译器也可能在前端执行。

`5a = int;` 在许多词法器中会被切为数字、标识符、等号、关键字、分号，错误更可能在语法分析阶段；只有当语言词法规范把 `5a` 整体视为非法数字字面量时才是词法错误。

### 7.2 为什么需要多个 IR

IR 没有唯一标准。“高层 IR”保留类、闭包、异常、装饰器等源语言概念；“低层 IR”把它们降低为显式控制流、内存读写与调用。一个编译器通常拥有多个 IR 方言并逐级 lowering。

评价 IR 可看三方面：

1. **通用性（versatility）**：能否承载多语言/多任务，又不抹平任务所需语义；
2. **性能（performance）**：是否便于构建索引、求不动点、维护 def-use，并控制规模；
3. **开发效率（productivity）**：是否有稳定 schema、遍历/查询 API、源码映射和扩展机制。

“语言无关”不是越彻底越好：统一表示若丢失异常、反射、生命周期或动态分派语义，可能使分析不可靠。

## 8. CST 与 AST

以表达式 `15 * (3 + 4)` 为例。

**具体语法树（CST/parse tree）**忠实呈现文法推导，可能包含 `E` 等非终结符、括号和标点。它不仅可做语法校验；保留全部 token/trivia 的 CST 对格式化、重构、代码修复和增量编辑尤其重要。

**抽象语法树（AST）**去掉许多文法中间层，把运算结构直接表示为：

```text
      (*)
     /   \
   15    (+)
         / \
        3   4
```

括号虽然不再是节点，其约束的优先级已进入树形结构。AST 易于做名称解析、类型标注、模式查询和源码级变换，但通常与语言语义紧密相关。

常见解析生态包括 ANTLR、Tree-sitter，以及 Clang、Eclipse JDT/JavaParser/Spoon、Babel/TypeScript compiler API、Python `ast`/LibCST、Go `go/ast`、Rust `syn` 等。Tree-sitter 的优势之一是增量、容错解析；严格说它产出的树是否称 AST/CST 取决于 grammar 与节点保留策略。原材料中的 `Esprinma` 应为 **Esprima**。

## 9. 控制流图与基本块

AST 表达语法嵌套，却不适合作为复杂跳转的主要表示。控制流图：

\[
G=(B,E,entry,exit)
\]

其中节点通常是基本块，边表示一次可能的控制转移。必须区分：

- **直接后继关系**：存在 CFG 边 \((b_1,b_2)\)；
- **可达关系**：存在从 \(b_1\) 到 \(b_2\) 的零条或多条边路径。

把“存在潜在路径”称为“控制流顺序”容易把传递可达关系与直接边混在一起。

### 9.1 基本块

基本块是一段最大化的直线代码：控制只从第一条进入，除最后一条外中间没有分支，进入后依序执行到末尾。传统“单入口、单出口”中的“单出口”常指只有块尾能转移控制，不表示块只能有一个后继；条件分支块通常有两个后继。

三地址指令序列的 leader 规则：

1. 函数第一条指令；
2. 任意跳转目标；
3. 任意条件/无条件跳转之后的下一条指令（即使可能不可达，也便于分块；之后可由可达性分析删除死块）。

从一个 leader 到下一个 leader 之前构成基本块。块尾的条件跳转、无条件跳转、fall-through、`return` 分别产生相应 CFG 边。异常、间接跳转、`switch`、协程和非局部退出还要求更丰富的边模型。

考虑：

```text
(1) x=1        (2) y=x-1
(3) z=x*y      (4) if z<x goto 7
(5) a=5        (6) goto 3
(7) a=q        (8) b=x+a       (9) c=2*a-b
(10) if p==q goto 12
(11) goto 3    (12) return
```

leaders 为 1、3、5、7、11、12，基本块为：

```text
B1=(1,2)       B2=(3,4)       B3=(5,6)
B4=(7,8,9,10)  B5=(11)        B6=(12)
```

主要边：`B1→B2`，`B2→B4`（真）、`B2→B3`（假），`B3→B2`，`B4→B6`（真）、`B4→B5`（假），`B5→B2`；`B6` 无普通后继。

## 10. 三地址码（3AC）

三地址码把复杂表达式拆成简单指令。典型形式：

```text
result = arg1 op arg2
```

“三地址”指最多出现三个**地址/名字**（结果、两个操作数），不是说整条指令只有三个“元素”；操作码 `op` 并不是第四个地址。还可有复制、单目运算、加载/存储、参数、调用和跳转等形式。

源代码：

```c
if ((a + b) * c < 10) x = 1;
else                    x = 2;
y = x;
```

可线性化为：

```text
t1 = a + b
t2 = t1 * c
t3 = t2 < 10
if t3 goto L1
goto L2
L1: x = 1
goto Lend
L2: x = 2
goto Lend
Lend: y = x
```

标签和跳转可诱导 CFG；3AC 风格本身不保证已有显式基本块对象。与 AST 相比，3AC 通常更低层、更规范化，更容易看见求值顺序和临时值，但仍可能保留语言或 IR 特有语义。

在合流点，普通 3AC 的 `y=x` 有两个到达定义。传统 reaching-definitions 分析可在 CFG 上求得它们；SSA 则把这种关系直接编码。

## 11. SSA 与 φ 函数

**静态单赋值形式（SSA）**要求每个 SSA 名字恰有一个静态定义点；源程序变量的多次赋值通过重命名变成不同版本。它是一种 IR 形式/性质，不宜绝对地说“不是独立 IR”。

上例转换后：

```text
t1_1 = a_0 + b_0
t2_1 = t1_1 * c_0
t3_1 = t2_1 < 10
if t3_1 goto L1 else L2

L1: x_1 = 1; goto Lend
L2: x_2 = 2; goto Lend

Lend:
  x_3 = phi [x_1, L1], [x_2, L2]
  y_1 = x_3
```

\(\phi\) 不是普通运行时函数；它位于合流块开头，根据控制实际来自哪个前驱边选择对应值。其参数必须与前驱块对应。SSA 建立唯一 def-use 关系，支持常量传播、死代码消除、值范围分析等稀疏算法。

重要边界：

- SSA 不消灭 CFG；\(\phi\) 的含义依赖前驱边，控制流仍是必要语义；
- “每个变量只赋值一次”针对 SSA 值名。可变内存、数组元素、对象字段不会自动变成普通 SSA 值，需要 alias analysis、Memory SSA 或先把可提升局部变量寄存器化；
- 构造最小 SSA 通常涉及支配树与 dominance frontier，而不是简单加版本号；
- 过多名字与 \(\phi\) 会增加表示规模，离开 SSA 时还需处理并行复制与关键边。

## 12. LLVM IR

LLVM IR 是有严格类型和语义的低层、SSA 风格 IR，函数由基本块构成，每块以 terminator（如 `br`、`ret`）结束。它连接多语言前端、优化器和多架构后端，但不等于所有“三地址码 + SSA”的抽象总和。

对应示例（为教学简化）：

```llvm
define i32 @f(i32 %a, i32 %b, i32 %c) {
entry:
  %t1 = add i32 %a, %b
  %t2 = mul i32 %t1, %c
  %t3 = icmp slt i32 %t2, 10
  br i1 %t3, label %then, label %else

then:
  br label %merge
else:
  br label %merge

merge:
  %x = phi i32 [ 1, %then ], [ 2, %else ]
  ret i32 %x
}
```

常量不必用 `add 0, 1` 人为制造 SSA 定义；\(\phi\) 可以直接接常量。实际未优化前端 IR 常把局部变量表示为 `alloca/load/store`，经过 `mem2reg` 等变换才提升为寄存器 SSA。LLVM 的整数溢出标志、`poison`、`undef`、内存模型与调用属性都会影响分析结论，不能把它当作“无语义细节的简单汇编”。

## 13. YASA-UAST：多语言统一的高层 IR

YASA 的核心选择是统一抽象语法树（UAST）：先利用各语言原生/专用解析器得到语言特定 AST，再按统一节点规范进行合并、改造和保留，转换成 UAST。由此，Checker 可在较统一的结构上执行 AST 查询，并与数据流、调用图等能力结合。

与 ANTLR、Tree-sitter 的“支持多种 grammar、各语言树形仍不同”相比，YASA-UAST 更强调**节点 schema 的跨语言统一**。选择 AST 层而非直接统一到 SSA 的理由是保留：

- 装饰器、注解；
- async/await、生成器；
- 类、模块、闭包；
- 源码位置与仍需保留的语言特性元数据（许多语法糖会被主动去除）；
- 适合源码审计和规则编写的高层概念。

代价也必须明确：同名 UAST 节点在不同语言中的求值顺序、异常、动态分派和生命周期规则可能不同。可靠的统一 IR 需要保存语言标签、类型/绑定信息、源码映射及必要的语言特有扩展；否则“统一”会变成语义丢失。AST/UAST 适合高层规则，CFG/SSA 适合精细数据流，两者通常是互补层，而非二选一。

## 14. 一条端到端分析路线

以“检测变量在使用前可能未初始化”为例：

1. **解析**：源代码变成 AST/UAST，保留声明、赋值、使用与源码位置；
2. **名称绑定**：区分同名但不同作用域的变量；
3. **降低**：把表达式副作用和控制结构变成明确指令；
4. **CFG**：构建分支、循环、异常等边并划分基本块；
5. **抽象域**：每个变量取 `Uninit / Init / Top` 等状态；
6. **转移函数**：声明产生 `Uninit`，赋值产生 `Init`，使用点读取状态；
7. **汇合与不动点**：按 may/must 目标选择事实编码与 join，迭代至稳定；
8. **跨过程扩展**：处理参数、返回值、调用边和别名；
9. **报告**：把 IR 位置映射回源代码，给出路径或解释；
10. **精化/验证**：排除不可行路径，或生成测试复现告警。

这条路线把前文概念串起来：不可判定性解释为何需要近似，soundness 契约决定近似方向，IR 决定能表达哪些语义，而抽象域与转移函数决定精度和成本。

## 15. 原文易误解或技术错误（集中纠正）

1. **随机数示例输出写反**：真实输出是 `yes` 或 `maybe`；`r == 1` 不可行，所以 `no` 不会出现。
2. **欠近似定义不准确**：欠近似是带真实见证的行为子集，不是“只取所有分支都不成立”或“只取必经路径”。
3. **may/must 结论过强**：过近似的 may 告警不保证存在真实路径；must 分析得出“不必然”也未必自动给出真实反例。
4. **soundness/completeness 用法混淆**：二者取决于把何种结论视为正例。文中“sound=无漏报、complete=无误报”属于安全验证惯例的一种说法，不是跨领域唯一标准；必须显式定义 FP/FN。
5. **“不存在同时 sound 与 complete 的算法”缺限定**：应限定一般图灵完备程序、非平凡语义性质、分析器总终止。有限状态或受限语言上可以两者兼得。
6. **Rice 定理适用范围被扩大**：它针对程序计算函数/识别语言的非平凡外延语义性质，不直接覆盖源代码语法性质；内存泄漏等需先固定操作语义和量词，再做归约。
7. **内存泄漏对角例不严谨**：原例让程序 `Q` 在运行时调用 `Leak(Q)`，没有交代程序编码、自指构造和“泄漏”在不终止执行中的定义，且文字误称程序为 `Evil`。宜使用从停机到缺陷可达性的显式归约。
8. **动态分析“没有误报”过度绝对**：执行轨迹可作为强证据，但 oracle、插桩、环境与分类仍会产生误报；反之单次不触发也不能证明缺陷不存在。
9. **静态/符号执行“探索所有路径”过度绝对**：路径爆炸、循环及预算使多数符号执行只能覆盖部分路径；静态分析也不都做全路径过近似。
10. **符号域混合了不同概念**：`unknown` 是知识不足，`undefined` 是具体异常/值；应通过异常域或产品域明确建模。\(\bot\) 与 \(\top\) 也不可省略。
11. **词法错误示例不稳妥**：`5a = int;` 常能词法切分，随后才产生语法错误。
12. **语义分析能力说得太广**：类型与作用域错误属于静态语义；一般逻辑错误不可由编译器语义阶段普遍捕获。常量折叠通常是优化，但阶段划分依实现而异。
13. **CST 用途被低估**：CST 不只做合法性校验；源码保持式重构、格式化和 IDE 增量编辑往往更依赖 CST。
14. **工具名拼写**：`Esprinma` 应为 `Esprima`。Tree-sitter 生成的是 CST 还是 AST 取决于 grammar/节点选择，不能一概而论。
15. **“控制流顺序”混淆直接边和可达路径**：CFG 边表示直接转移，路径可达性是其传递闭包。
16. **基本块“单出口”易误读**：条件分支块可有两个后继；含义是控制只在块末离开，而非只有一个目标。
17. **语句级 CFG 的表达式缺失不是 CFG 必然缺陷**：若节点粒度定义到表达式/IR 指令即可表达；这是表示粒度选择。
18. **3AC 定义为“最多三个元素”不严谨**：是最多三个地址（结果和两个操作数），操作码另算；3AC 也不必天然拥有显式基本块结构。
19. **SSA 的定位过于绝对**：SSA 可称 IR 形式或一种约束；它不只“优化变量规范”。构造还依赖支配关系。
20. **SSA 不等于所有存储单赋值**：内存必须经提升、别名分析或 Memory SSA 另行表示。
21. **\(\phi\) 不取代 CFG**：它依赖前驱边并编码值的合流；“控制流已包含在变量名中”会误导。
22. **LLVM 示例冗余**：用 `add i32 0, 1` 表示常量虽可能合法却不自然；\(\phi\) 可直接接 `[1, %then]`。真实 LLVM 还包含 `poison/undef`、内存等关键语义。
23. **IR “没有好坏”表述太弱**：IR 确实按任务取舍，但对给定语义和任务仍可比较正确性、信息保真、规范化程度、规模和分析成本。
24. **“误报=不 complete、漏报=不 sound”并非无条件成立**：这再次依赖告警/证明哪一个被定义为正结论，应在全文统一契约。
